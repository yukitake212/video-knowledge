## 使い方

### まず案件の条件を確認する

**工程を判定する前に確認する。該当すれば全工程で参照する。**
これらは工程の条件ではなく案件全体の条件なので、途中の工程で拾い直すと漏れる。

- **原作の媒体は何か。公式の視覚素材はあるか**
  → 未映像化の書籍・漫画なら `reference/principles/book-trailer.md`
- **案件のロックブロックを先に作ったか** → `reference/templates/lock-blocks.md`
  （**声・参照のコネクタ・禁止・命名。一度書いて以後そのまま貼る。**
  読んで判断するものは飛ばせるが、貼るものは飛ばすと出力が不完全になる）
- **案件ヘッダを1枚書いたか** → `reference/templates/trailer-brief.md`
  （訴求・支配軸のずれ・開示・媒体条件・具体化の範囲・**配置の方針**。
  **カットを1つも作る前に。自社未検証なので、埋まらない欄は消してよい**）
- **本番参照や学習に第三者の素材を使うか** → `reference/templates/style-reference-card.md`
  （**許諾の根拠が空の素材を本番へ流さない**。→ `reference/OPERATIONS.md`）
- **媒体モードとルックが未確定か**（実写調かアニメ調か、原作素材を動かすのか）
  → `reference/principles/visual-style.md`。**「アニメか実写か」を二択で先に決めない。**
  原作の識別的な文法を抽出してから、それを最も損失少なく実装できるモードを選ぶ
  （**このファイルは自社未検証**）
  （**顔・場所・出来事・音を新たに解釈して作ることになる。** 完成映画の予告と条件が違う。
  下の静止画素材の判定とは別——あちらは素材処理、こちらは表象範囲）
- 縦型（9:16）で納品するか → `reference/principles/vertical.md`
  （アセットを縦で作る＝工程3、構図の書き方＝工程4、の両方で効く）
- 完成した静止画（漫画原稿・書影・挿絵・写真）を素材に使うか
  → `reference/principles/still-to-motion.md`
  （clean plate 化＝工程3、参照の役割分離＝工程4、の両方で効く）
- 生成物に電子透かしや来歴情報が入って困る案件か
  → `reference/models/image/nano-banana.md`（C2PA と SynthID が必ず入る）
- ジャンル別の実績があるか

### 次に工程を判定する

工程が決まらないと読むファイルが決まらない。

| ユーザーがやろうとしていること | 工程 |
|---|---|
| 原作を読んで画の案を出す／何を撮るか決める | 1. Think |
| 構成・カット表・秒割りを作る | 2. 構成 |
| キャラクターシート・場所・物・文字の素材を作る | 3. 画像 |
| 画像を直す・修正する | 3. 画像（修正から入る） |
| 動画に渡すフレームを作る | 3. 画像 |
| 生成に投げるプロンプトを書く／直す | 4. プロンプト |
| 生成が失敗したので直す | 4. プロンプト（修理から入る） |
| つなぎ・音・納品の相談 | 5. 編集 |

**生成結果が壊れた原因を調べる場合は工程ではない。** 末尾の「症状から引く」を使う。

判定できないときは、**ユーザーに工程を聞く。**

**工程を判定してから読むのは、量を節約するためではない。** 工程1で先の工程のものを読むと
**制御が発想を食う**（下記）。**それ以外の工程では、関係しそうなものを読んで構わない。**

## 1. Think（発想）

**読む：** `reference/principles/workflow.md` だけ。

**読まない：** `shot-structure.md` / `guards.md` / `directing.md` / `action-sequence-schema.md` /
`trailer-structure.md` / `book-trailer.md` / `cross-media-style-translation.md` /
`platforms/` のすべて。

この禁止は重要。リポジトリに自社の失敗として記録がある。
**着想と制御を同じ一手でやろうとすると、制御が発想を食う。** 破綻しない案を1つ出して
それを守る側に回ってしまい、撮りたいものが一行も書かれないまま進む。

**これは分量の話ではなく挙動の話。** 読む量が問題なのではなく、
**評価と禁則を先に読むと発想がそちらへ寄る**のが問題。
**だから他の工程には同じ禁止を持ち込まない。**

### 手順

**発散を始める前に、実行表を先に書く。** 書かずに始めると、読みやすい分量へ勝手に圧縮される。

| 項目 | 決めること |
|---|---|
| 使う制約 | **3つ以上。** 案件の既定値を壊す方向で選ぶ |
| 1制約あたりの案数 | 20 |
| 総件数 | **制約数 × 20**（3制約なら60案） |
| 出力の分け方 | 制約ごとに完全に分ける。1つのリストに混ぜない |
| 評価 | **禁止。** ★も順位も「特に強いのは」も付けない |

**ユーザーが件数を指定してきても、それは1制約あたりの数として読む。**
「20個出して」は「制約ごとに20個」であって「合計20個」ではない。
総件数が指定より多くなることを先に伝えてから進める。

1. **原作から画だけを抜く。** 実現可能性もネタバレ判定も一旦外す
2. **上の実行表を書く**
3. **制約ごとに20案、評価抜きで出す。** 全制約を出し切るまで止まらない
4. **全部出し切ってから**、この映像が何なのかを一行で決める
5. 謎型か人物型かを決める

**3で止まって4へ進むのが最頻の失敗。** 1つ目の制約で20案出すと、
それらしい分量になるので終わった気になる。**総件数を検算してから次へ進む。**

### チェックリスト

- [ ] **実行表を先に書いたか。** 制約を3つ以上選んだか
- [ ] **総件数が「制約数 × 20」になっているか。** 検算したか
- [ ] 「いくつか案を出す」で止まっていないか。**数を指定したか**
- [ ] 制約を分けて出したか。1回の出力に混ぜていないか
- [ ] 「場面」ではなく「一枚の画」で書いたか（「葬儀のシーン」ではなく具体物）
- [ ] 使えない案も混ざっているか。混ざっていなければフィルタが効きすぎている
- [ ] **プロンプトの話を一切していないか**

### この工程で出してはいけないもの

生成用プロンプト。仕様が固まる前にプロンプト化すると、生成クレジットの無駄になる。

## 2. 構成・カット表

**読む：**

| 条件 | 読む |
|---|---|
| 常に | `reference/principles/trailer-structure.md`（構成の原則。**ほぼ全部が外部情報で自社未検証**）／`reference/templates/shot-schema.md`／`reference/principles/sound.md`／`reference/principles/typography.md` |
| **原作がある** | `reference/templates/source-breakdown.md`。**選ぶ前に分解する。** 印象的な画を直接出すだけだと候補が偏る |
| **台詞を使う** | `reference/principles/directing.md`「切り出された台詞に演技を与える」。**どの台詞を使うか決めるのはこの工程。** プロンプトを書く段階ではない |
| **原作が未映像化の書籍・漫画** | `reference/principles/book-trailer.md`。**顔・場所・出来事・音を新たに解釈して作ることになる** |
| **原作から画を起こす**（コマをそのまま使わない） | `reference/principles/cross-media-style-translation.md`。preserve / translate / invent / omit の4分類。**筋を進めないカットの機能もここ** |

※ 縦型・静止画素材の条件は冒頭の「案件の条件」で判定済みのはず。

### 手順

1. **訴求を決める。** 主訴求を1つ、副訴求を1つまで。工程1で出した一行と引きの型を
   「**この予告編が何を証明するか**」まで詰める（→ trailer-structure.md）。
   **何を試し撮りするかがここで決まる。** 構成の確定ではないので、次へ進んでよい
2. **試し撮りをする。** 3〜5カットだけ生成して強度を測る。素材を一枚も見ないうちに
   構成を確定させると、生成してみて前提が崩れる
   - ここで書くのは**強度測定用であって完成プロンプトではない**。書き方は工程4を参照する。
     試し撮りの段階でアセットを作り込まない
   - 試し撮りの段階で**候補モデルを1〜2個に絞る**。ここで見るのは
     「この発想がこの系統で成立するか」（→ principles/prompt-compilation.md）
3. **radio cut を作る。** 台詞・ナレーション・音楽の幕・主要効果音・無音だけを並べ、
   **画を消して論理と感情が通るか**を聞く。無音前提の納品なら文字と画の骨格で代替する
   （→ `reference/principles/sound.md`）
4. カット表を作る。**画・音・文字を同じ表の上で決める**
5. 構成を提出して確定させる

### チェックリスト

- [ ] 冒頭3秒：**媒体の視聴開始条件に合う「最初の認識イベント」があるか。**
      スクロール中・スキップ可能・無音開始なら動きが有力。**動きを使わないなら理由を書く**
- [ ] 音を消していても0.5秒以内に何かが読めるか
- [ ] 5〜8秒ごとに何かが変わるか（離脱の崖）
- [ ] 約束は1つに絞ったか
- [ ] 音のトラック行があるか。どこにライザー、どこにヒット、どこが無音か
- [ ] 文字カードの行があるか。COPY / FIELD / MOTION / AUDIO CUE
- [ ] 縦型なら上・中・下の欄があるか。**下20%を空けたか**
- [ ] 静止から始めるなら3条件を満たすか（→ 下の「静止から始める場合」）

### 静止から始める場合

冒頭を完全に静止した素材として見せ、遅れて動き出す構成。次の3条件を満たすこと。

1. **3秒以内に動き出す**
2. **音を消していても0.5秒以内に何かが読める**
3. **「ようやく動いた」ではなく「動くはずのないものが動いた」と読める形にする**

根拠は `reference/principles/workflow.md` の「静止から始めてよい場合」。
素材由来のカットでの扱いは `reference/principles/still-to-motion.md`。

## 3. 画像

**まず `reference/principles/image-production.md` を読む。** 工程の全体像がそこにある。

この工程は4段階ある。**順に進める。**

### 3A. 何を作っているか決める

**媒体モードとルックが未確定なら先に** `reference/principles/visual-style.md`。
**時間文法（止め・コマ打ち・部分運動）はここで決めないと工程4で取り返せない。**

12のタスクのどれか（→ image-production.md）。**判定できないときはユーザーに聞く。**

同時に決める。

- **探索か本番か**
- **新規生成か編集か**
- 同一性が重要か
- 複数参照を使うか
- 世界・場所に関わるか

**編集なら `reference/principles/image-repair.md` へ。** 生成とは規律が違う。

### 3B. 仕様を埋める

タスクに応じて読む。

| タスク | 読む |
|---|---|
| キャラクターシート・キャスティング | `reference/templates/character-sheet.md` |
| 物・小道具 | `reference/templates/asset-card.md` |
| 世界・場所 | `reference/principles/world-assets.md` |
| ショットのフレーム | `reference/templates/shot-ir.md`、`reference/principles/shot-structure.md` |
| 文字が主 | `reference/principles/typography.md` |
| 静止画素材を動かす | `reference/principles/still-to-motion.md` |

**優先度（MUST / SHOULD / MAY）をここで決める**（→ principles/prompt-compilation.md）。

### 3C. 出力先を決める

**モデルが決まる前にプロンプトの形は決まらない。** 用途別の第一候補（すべて未検証の仮説）。

| 用途 | 候補 | 参照 |
|---|---|---|
| 動画のキーフレーム | Nano Banana Pro / Soul Cinema | 両方とも公式がキーフレーム用と明言 |
| 物の切り抜きアセット | GPT Image 2 | 透明背景（preview） |
| キャラクターシート | GPT Image 2 / Soul ID | 公式にキャラアンカーの工程がある |
| 局所修正 | GPT Image 2 / Seedream 5 Pro（編集用） | 座標・マスク指定 |
| 探索・ルック開発 | Krea 2 | 探索寄りの設計 |
| アニメ・イラスト調 | Krea 2 Medium | イラスト・アニメに強いとされる |

**専用ツールで済むなら生成モデルに投げない**（→ principles/image-repair.md）。

### 3D. 変換して書く

対象モデルの `models/image/` ファイルを読む。**指示を渡す経路がプロンプトだけとは限らない**
（→ principles/prompt-compilation.md の分類B）。

### チェックリスト（3Dの後）

- [ ] このタスクに合ったモデルを選んだか
- [ ] プロンプトに書いているものが、参照やUIで担保できていないか
- [ ] 生成パラメータ（解像度・アスペクト比）をプロンプト本文に書いていないか
- [ ] 参照ごとに「使う情報／使わない情報」を書いたか
- [ ] 編集なら **PRESERVE を書いたか。反復のたびに繰り返しているか**
- [ ] 文字は引用符で囲んだか。書体を指定したか
- [ ] 証拠アセットを綺麗に作りすぎていないか（強いボケ・劇的な照明で情報が減っていないか）
- [ ] シート内に顔は1枚だけか。生成に渡す版に文字が入っていないか
- [ ] **クライアント素材を扱うなら、入力先の条件を確認したか**（→ OPERATIONS.md）

### 修正（生成後）

**作り直す前に、専用ツールと局所編集を検討する。**
承認済みの状態を残し、壊れた状態の上に修正を重ねない
（→ principles/image-repair.md）。

## 4. プロンプト執筆

**まず `reference/principles/prompt-compilation.md` を読む。** 工程の全体像がそこにある。

この工程は4段階ある。**順に進める。飛ばさない。**

### 4A. ショット仕様を埋める — モデル非依存

**読む：** `reference/templates/shot-ir.md`。

モデルを決める前に、狙い・時間の割り・被写体・参照・位置関係・音・不変条件・
優先度（MUST / SHOULD / MAY）を埋める。

**優先度をここで決める。** 書き始めてからでは決められない。

### 4B. 出力先を決める

**読む：** `reference/platforms/` のうち候補のもの。

`ホスト × ベースモデル × 版 × 生成モード` の4つを決める。
**モデル名だけでは足りない。** 同じモデルでもホストによって参照上限・入力種別・
プロンプトの書き換えが変わる。

**生成モードは、品質の序列ではなく「境界か再利用か」で選ぶ。**

| MUST | 候補 |
|---|---|
| 完成画をそのまま開始／終了フレームにする | **I2V / FL2V** |
| 人物・物・場所・画風・構図・動き・音を**別構図へ再利用する** | **Ref2V** |
| 両方 | 併用可否を確認。**排他ならMUSTを優先するか工程を分ける** |

**公開プロンプトの多数派で決めない**（→ `reference/principles/prompt-compilation.md`
「生成モードは『境界』と『再利用』で選ぶ」）。

H3 は T2VA / I2VA / FL2VA / L2VA / Ref2VA で文法が変わる。**Wan は first/last frame と
参照が排他。**

### 4C. 読む知識を選ぶ

**下は「常に読む」と「条件つき」の区別であって、読む量の上限ではない。**
迷ったら読んでよい。1工程ぶんを全部読んでも十数万字で、案件1本の規模に対して問題にならない。

**害があるのは、読んだものを全部プロンプトへ書くこと。** そこは別の予算
（→ `reference/principles/prompt-compilation.md`「予算は文字数ではない」
「削る順序は文字数ではなく優先度」）。**読む量と書く量を混同しない。**

| ショットの性質 | 読む |
|---|---|
| 常に | `reference/principles/shot-structure.md` |
| **実写調で作る** | `reference/templates/house-style-live-action.md`（**12軸を1つ埋めた実例。普遍的な分類ではない** → `reference/principles/visual-style.md`） |
| **アニメ調で作る** | **ハウススタイルブロックは無い。** `reference/principles/visual-style.md` の12軸から書く。**滑らかにするのが忠実化ではない** |
| **完成した静止画が素材（漫画原稿・挿絵など）** | **ハウススタイルブロックを貼らない。** 素材そのものが look の正本（→ `reference/principles/still-to-motion.md`） |
| 芝居がある | `reference/principles/directing.md` |
| 破綻の心配がある | `reference/principles/guards.md` |
| 身体的な負荷のあるアクション | `reference/templates/action-sequence-schema.md` |
| 煙・霧・粉塵・光 | `reference/principles/atmospheric-fx.md` |
| 完成した静止画が素材 | `reference/principles/still-to-motion.md` |
| 文字カード | `reference/principles/typography.md` |
| 言い換えに詰まった | `reference/templates/vocabulary.md` |

**失敗ガードは、そのモデルで実際に起きたものだけ読む。** 予防的に全部入れない
（→ `reference/platforms/model-quirks.md`、対象モデルの `platforms/` ファイル）。

### 4D. 変換して書く

**読む：** 対象モデルの `reference/platforms/` ファイルの「公式の式」。

**まず案件のロックブロックを貼る**（→ `reference/templates/lock-blocks.md`）。
ハウススタイル・声・参照のコネクタ・禁止。**一字一句そのまま。**
**「前のショットと同じ」はモデルに通じない。毎回全文を書く。**

ショット仕様を、そのモデルの文法へ変換する。**前のモデル用のプロンプトを
手直ししない。** モデルを変えるなら 4A へ戻る。

### チェックリスト（4Dの後）

**書けているかの検証。** ここで初めて使う。

- [ ] ハウススタイルブロックを**1回だけ**貼ったか。**素材が原稿・イラストなら貼っていないか**
- [ ] そのモデルの公式の式に沿っているか。**秒指定を使うかどうかもモデル次第**
- [ ] 生成パラメータ（解像度・fps・アスペクト比）をプロンプト本文に書いていないか
- [ ] 1区間の主要な動きは1つか。カメラの動き1つ・被写体の動作1つか
- [ ] 参照ごとに「使う情報／使わない情報」を書いたか
- [ ] 参照の役割を12種類から選んだか
- [ ] 否定は末尾にまとめたか。**肯定側とセットになっているか**
- [ ] 単独で立っている否定はないか
- [ ] Physics 節があるか。`nothing floats` で締めたか
- [ ] 生きている下限を書いたか（瞬き・呼吸・眉の微細表情）
- [ ] 矛盾する指示が混ざっていないか
- [ ] **移動する人物に、荷重・接地・推進主体・持ち上げ可否を書いたか**
      （→ `reference/principles/guards.md`「移動と荷重」）
- [ ] **MUST 属性に `or` や「2〜3人」を書いていないか**（→ 同「曖昧さを自分で作らない」）
- [ ] **MUST が全部入っているか。** プロンプトから外したものは、参照・UI・APIで
      担保されているか

### 受け取ったら、2つの軸で見る

**壊れていないことと、書いた出来事が起きていることは別。**

| 軸 | 問うこと |
|---|---|
| **品質** | 破綻していないか（形・数・遠近・大きさ・造形） |
| **意味忠実度** | **書いた出来事が起きているか。荷重・接地・因果・主体** |

**意味忠実度の失敗は症状を出さない。** 下の索引では引けないので、**先に自分で問う。**
「強制的に歩かされる」と書いて**引きずりが返ってきても、絵は破綻しない**
（→ `reference/OPERATIONS.md`「品質と意味忠実度を分ける」）。

### 修理（生成後）

**全文を書き直さない。**

```
不具合 → 関係する仮説 → 該当箇所 → その箇所だけ差し替え
```

全文書き直しは、直っていた MUST まで変える。症状からの当たりは下の索引。

### 書けていないときの型

形容詞が積み上がっていたら、**動きとレンズで書き直す。** 抽象語は数えられる条件に翻訳する。
速さは「fast」ではなく観測できる帰結を列挙する。

## 全工程に共通すること

### models/ が名指しされていないのは意図

`models/video/` `models/image/` の各ファイルは本文から名指ししていない。
工程3C・3Dと4B・4Dで「**対象モデルの `models/` ファイルを読む**」と抽象的に書いてある。
**モデルが増えるたびにこのファイルを直さなくて済むようにしてある。欠落ではない。**

### 出所で割り引いて読む

各行に出所が書いてある。読むときに区別する。

| 表記 | 扱い |
|---|---|
| 自社検証 | 信頼できる |
| corpus/xxx | 他人の公開プロンプトの分解。作法としては妥当だが未検証 |
| 外部情報 | 記事・公式ページ。**自社では確かめていない** |
| 推測 | 検証していない |
| 他社の実績値 | **自社の数字として使わない。** 見積もりの根拠に使うときは断る |
| **他のLLMの調査結果** | **一次情報を確認するまで推測として扱う。** → 下 |

**「他のLLMの調査結果」は他の4つのどれでもない。** 外部情報とは違う——文献そのものではなく
文献についての要約だから。推測とも違う——出典が付いているから。**しかしその出典が実在するか、
記述が原著と一致するかは、確認するまで分からない。**

実際に受け取った2件では、**一部は一次情報に当たって確認でき、一部は論文を特定できなかった。**
そして確認できた1件は、**原著の主張より広く書かれていた**（語単位の局所窓の話が、
物語規模の話であるかのように読める形になっていた）。

**確認したものと、できなかったものを分けて記録する。** 確認できたら、その原著の等級で書き直す。

`OPERATIONS.md` の相場・歩留まり・承認ラウンド数は**すべて他社の値で自社未検証**。
クライアントに数字として出さない。

**モデル開発元の公式と、ホストの公式と、その二次紹介を区別する。**
`platforms/` の各ファイルは、どれがどれかを節ごとに書いてある。
「公式ガイドによれば」と書かれていても、**原典を確認したものと、
それを紹介した記事から取ったものがある。**

### 割れている論点は、片方を選んで書かない

**公開情報どうしが食い違っている項目が5件ある**——機材名・監督名、スタイルの配置、
レンズの書き方、速度の数値化、否定をゼロにするか
（→ `reference/OPERATIONS.md`「割れている論点」）。

**どれも n が小さい。** 参照ファイルに両方書いてあったら、**それは矛盾ではなく未決。**
案件では**どちらかに決めて、決めたことを記録する。**

### 断定しない

「これが正解で確定」と書かない。覆る前提で書く。新しいものが見えてきたときの障害になる。

### 未検証のものを本番で使ったら

**結果を記録する。** 効いた／効かなかったを作業文書に残し、案件終了時に差分ファイルにして
リポジトリへ戻す。形式は `DIFF-FORMAT.md`。

検証済みになった項目は `reference/models/video/seedance.md` から `reference/platforms/model-quirks.md` へ移す。
**仮説ファイルが痩せていくのが正しい状態。**

### 案件固有の情報

クライアント名・未発売作品の筋書きは、**どの版にも入っていない。**

ジャンル別の知見（`crime-mystery` / `practical-manga` / `sf-action`）は private の
video-projects にある。**Claude Code 用のローカル版だけが直接参照する。**
zip版とChatGPT版には入っていないので、必要ならユーザーに貼ってもらう。
