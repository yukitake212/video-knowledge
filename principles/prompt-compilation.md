# プロンプトを組み立てる工程

出所と時期を各項目に書くこと。以下は2026-08に収集。

**知見が増えてもプロンプトは長くならない。** 知見が増えて良くなるのは、
選ぶ精度・変換の精度・失敗を潰す精度であって、書く量ではない。
むしろ最終プロンプトは短くなり得る。

## 最終プロンプトは成果物であって原本ではない

これが全体の前提。

```
知見全体
  ↓ 選ぶ
このショットの仕様
  ↓ 変換する
モデル・ホスト・モードごとの入力
  ↓
最終プロンプト
```

**モデルを変えるとき、前のモデル用のプロンプトを手直ししない。** ショットの仕様まで
戻ってから、別のモデル用に変換し直す。プロンプトはビルド成果物なので、
直接編集するとどこが元の意図だったか分からなくなる。

## 情報を4種類に分ける

プロンプトに何を書くかは、**その情報を誰が担保しているか**で決まる（2026-08 整理）。

| 種類 | 例 | プロンプトでの扱い |
|---|---|---|
| A. 参照が既に持っている | 顔、服、場所の質感 | 再説明を減らす |
| B. プロンプト外で固定される | 尺、アスペクト比、解像度、first/last frame、UIのカメラ設定。**画像側ではさらに広い**（下記） | 書くかどうかはモデルごとに決める |
| C. 言葉でしか伝わらない | 動作の順序、位置関係、誰が喋るか、終端状態、参照どうしの関係 | **必ず書く** |
| D. 失敗を塞ぐもの | そのモデルで実際に起きた失敗 | **起きたものだけ**書く |

### 画像ではBが大きい

画像制作では、指示を渡す経路がテキスト以外へ大きく分散している。

```
マスク / 点 / 矩形 / 投げ縄
スケッチ / 注釈
レイヤー
ムードボード
スタイル参照
学習させた同一性（トレーニング済みID・LoRA）
カラーパレット
UIのスライダー
カメラ・照明のUI
APIのハードパラメータ
```

**プロンプトに書くのは、これらで担保できないものだけ**
（→ principles/image-production.md）。

そして 2026-08 時点で、**この経路が増える方向に動いている。**
Cinema Studio 4.0 は感情・照明・色・カメラをUIへ外出しし、Midjourney は
創作の制御をアカウントのプロファイルへ移した（→ platforms/ と models/image/ 各ファイル）。

**知見が増えてもプロンプトは長くならない、の理由がもう1つ増えた。**
プロンプトに書くべきことが、他の経路へ移っていく。

理想は `C ＋ 必要なD ＋ A/Bの最小限の要約`。

**Dを予防的に全部書かない。** そのモデル・そのモードで実際に起きた失敗だけ。
起きていない失敗を塞ぐ行は、他の指示と注意を奪い合うだけになる。

## 削る順序は文字数ではなく優先度

**MUST / SHOULD / MAY** に分ける（2026-08 整理）。

- **MUST** — 失うとショットの意味・連続性・クライアント要件が壊れる。
  同一性、誰が喋るか、位置関係、動作の順序、終端状態、ワンテイクが意味を持つならカット無し、
  クライアントの禁則
- **SHOULD** — 品質を大きく上げるが、落ちても意味は残る。
  重さ、粉塵の反応、カメラ高、微細表情、特定の光の関係
- **MAY** — 仕上げ。グレイン、ハレーション、色のアクセント、光学的な粗

**予算が足りないときは MAY → 確度の低い SHOULD → 効果の小さい SHOULD の順で削る。**

**MUST はプロンプトから削っても、参照・UI・APIのどこかで担保する。** 削るのは
「プロンプトに書くこと」であって、「担保すること」ではない。

### ByteDance の削る順序

素材の予算を超えたときの順序が公式ガイドに書かれている
（2026-08 / ByteDance実践ガイドの二次紹介。**原典は未確認**）。

```
中核キャラ ＞ 主要な商品・小道具 ＞ 設定と環境 ＞ 全体のスタイル
```

**スタイルが最初に切るもの。** 人が最初に守ろうとするのがスタイルなので、
直感とは逆になる。

## 予算は文字数ではない

入力上限が2万文字でも2万文字使わない。**情報を増やすほど、カメラ・同一性・動作・光・
物理・音の間で注意の奪い合いが起きる**（2026-08 整理）。

ByteDance は自社評価として、一定量を超えると追加素材が結果を悪化させる（主要な特徴が
薄まりノイズが増える）と述べている（2026-08 / 二次紹介。**原典は未確認**）。
具体的な数字は `models/video/seedance.md`。

MiniMax は素材理解に大きな推論を使ったうえで、生成モデルへ渡す前に構造化された
中間表現へ蒸留する設計を公表している（2026-08 / MiniMax公式ブログの二次紹介）。
**入力枠が大きいことと、全部書くことは別。**

### 1件の観測 — 長い禁止の列が効いていない可能性

同じモデル・同じ種類の素材に対し、**1000語規模で禁止事項を列挙したプロンプト**と
**1〜3文の短いプロンプト**を使ったところ、**短いほうが安定した。** 長いほうでは、禁止を
足すほど挙動が極端な方向へ振れる現象が3回続けて起きた（「早く終わるな」と書くと運動が
終盤に押し込まれて破綻、「ゆっくり」と書くと停滞）。短いほうでは同種の振れが出ていない
（2026-08-28 / Hailuo H3。長い版で3回、短い版で5本以上）。

**厳密な対照実験ではない。** 長い版と短い版で対象カットも指示内容も異なるため、
「長さが原因」とは言い切れない。**禁止の量なのか、記述の複雑さなのか、対象の難易度なのかは
切り分けられていない。**

**そしてこの3回は、`platforms/model-quirks.md` の「FL2VAで最終フレームへジャンプする」と
同じ3回。** 「版面差が原因」と「プロンプトの長さが原因」は**独立した2件の証拠ではなく、
同じ観測に対する競合仮説**。**片方を根拠に片方を補強しない。**

**次に確かめること：同一カット・同一素材で、長い版と短い版を各3回。**
これで両方の仮説が同時に切り分く。

**それでも、書き方の指針としては先に採れる。** 否定を1つ書くたびに、**「そこは壊れる」という
前提を成果物に書き込んでいる**ことになる。**まず短く書いて、実際に壊れたところだけを
1箇所ずつ足す。** 1000語規模で禁止を列挙して時間配分まで指定したプロンプトが3回連続で
破綻したのに対し、**同じ狙いの動きが1〜3文の指示で1回で成立した**（同じ案件・同じモデル）。

これは「削る順序は文字数ではなく優先度」の逆向きの操作。**削るのではなく、最初から足さない。**

## 組み立ては最低3回ある

1回ではない。**工程として複数回あることを前提に設計する**（2026-08 整理）。

### 1回目 — 試し撮り

構成を確定させる前。この案が成立するか、モデルが合っているか、素材が強いかを見る。

最小限だけ書く。狙い／参照／主要な動作1つ／カメラの動き1つ／おおよその尺／対象モデル。
**本番用まで作り込まない。** 既存の「試し撮りを先にする」と同じ工程
（→ principles/workflow.md）。

### 2回目 — 本番

素材・配置・構成が確定してから。関係する原則、ショット種別の型、モデル側の変換、
ホスト側の制約、既知の失敗ガードを統合する。

### 3回目 — 修理

生成後。**全文を書き直さない。**

```
不具合 → 関係する仮説 → 該当箇所 → その箇所だけ差し替え
```

全文書き直しは、直っていた MUST まで変えてしまう。既存の PATCH LOG の考え方と同じ
（→ templates/shot-schema.md）。

### 4回目 — モデルを変えるとき

前のモデル用のプロンプトを手直ししない。ショットの仕様まで戻ってから変換し直す。

## モデル選択は2段階

**構成段階で仮に決め、カット表確定後に確定させる**（2026-08 整理）。

- **仮の割り当て** — 構成段階。候補を1〜2個に絞って試し撮りする。
  見るのは「このショットの発想がこの系統で成立するか」
- **確定** — カット表確定後。カットごとにモデルを決める

**モデルが決まらないとプロンプトの形が決まらない。** モデルごとに公式の式が違う
（→ platforms/ 各ファイル）。今までモデルを決めずにプロンプトを書き始めていたのは、
形が決まる前に中身を書いていたことになる。

## 出所の格付け

知見が増えるほど、どの出所かで扱いを変える必要が出る（2026-08 整理）。

| 段階 | 出所 | 使う対象 |
|---|---|---|
| A | モデル開発元の公式（MiniMax / ByteDance / Alibaba） | 生成モード、ハード上限、公式の文法、API制約 |
| B | ホストの公式（Higgsfield / Magnific / fal / BytePlus） | ホストのUI、上限、ホスト側の書き換え、ワークフロー |
| C | 自社で複数回再現 | **実務上いちばん強い証拠** |
| D | 自社で1回確認 | 暫定 |
| E | クリエイターの複数事例 | 共通見解の候補 |
| F | クリエイターの単発報告 | 検証待ち |
| G | 公開プロンプトからの逆算 | 失敗仮説の候補 |

既存の出所表記（自社検証／corpus/xxx／外部情報／推測）はこれと対応させられる。
**corpus からの逆算は G。** 現状 `principles/` の多くがここに載っている。

## ホスト側の書き換えを前提に置く

複数のホストが、渡したプロンプトを**内部で書き換えてからモデルへ送る**
（2026-08 / 各社公式の二次紹介）。

- Higgsfield は Cinema Studio 内部にプロンプト強化の仕組みを持つ
- Wan は API に `prompt_extend` を持つ
- fal 経由の H3 Max はプロンプト拡張のモードを持つ

つまり**こちらが書いたものが、そのままモデルへ届くとは限らない。**
書き換え結果を取得できる場合は、こちらのプロンプトとの差分が知見になる
（カメラ用語、音の構造、環境描写の足され方）。

**ただし書き換え後のプロンプトを public リポジトリへ保存してよいかは、
利用条件と著作権を別途確認すること。** 現時点では未確認。
